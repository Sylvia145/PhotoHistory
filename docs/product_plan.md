# 图片版本历史与 AI Diff 产品初方案

## 0. 一句话总结

第一版不做“图片版 Git”，而是做一个**跨修图软件的图片快照历史工具**。

它的核心价值是：

> 自动记录每一次图片修改，并用可视化 Diff 和 AI 总结告诉用户每个版本改了什么。

用户可以继续使用 Photoshop、Lightroom、美图秀秀、醒图、像素蛋糕、手机相册等工具修图。本产品不负责修图，而是在这些工具外面自动记录版本、对比差异、总结变化，并支持回退旧版本。

---

## 1. 产品定位

### 1.1 产品暂定名称

可选名称：

- PhotoHistory
- Retouch Timeline
- Image Time Machine
- 修图时间线
- 图迹
- 图片版本管家

### 1.2 产品定位

> 跨修图软件的图片版本历史与 AI 变化分析工具。

### 1.3 用户理解版定位

> 修图版 Time Machine。

### 1.4 核心卖点

- 自动保存每个修图版本
- 一键对比任意两版差异
- AI 总结每次修改内容
- 随时找回旧版本
- 标记最终交付版
- 未来支持客户审稿、协作和 Agent 工作流

---

## 2. 为什么第一版不做完整 Git

第一版不建议直接做完整 Git 概念，包括 commit、branch、merge、pull、push 等。

原因：

| 暂不做 | 原因 |
|---|---|
| 完整 Git 概念 | 对修图用户太重，理解成本高 |
| PS / LR 插件 | 开发成本高，早期不必依赖软件生态 |
| 自动还原修图步骤 | 仅凭最终图无法准确知道用户点了哪个按钮 |
| 自动合并版本 | 图片 merge 很复杂，容易产生不可信结果 |
| 大而全云盘 | 容易偏离核心价值，变成普通存储产品 |

第一版的核心不是“管理所有图片”，而是：

> 管理同一张图片的多个修图版本。

## 3. 目标用户

### 3.1 第一批优先用户

最适合第一版验证的用户不是纯普通用户，也不是最顶级专业修图师，而是：

> 高频半专业修图用户。

他们有真实痛点，理解价值快，也更可能付费。

| 用户类型 | 典型场景 | 核心痛点 |
|---|---|---|
| 小红书 / 抖音内容创作者 | 同一张图修自然版、氛围版、封面版 | 找不到哪版最好 |
| 电商运营 / 商品图制作人员 | 商品图反复改背景、加字、调色 | 版本混乱、交付混乱 |
| 摄影工作室助理 | 客户反复要求“自然一点、白一点” | 不知道哪版客户确认过 |
| 证件照 / 轻写真门店 | 一张脸修很多轮 | 客户要回上一版很麻烦 |
| 自由修图师 | PS、醒图、美图、像素蛋糕混用 | 软件内历史不互通 |

### 3.2 暂不优先的用户

纯普通用户可以作为增长人群，但不建议作为第一商业化对象。

原因是普通用户可能会觉得：

> 我手动多存几张图就行。

他们有需求，但痛点不够强，付费意愿相对弱。

## 4. 产品核心场景

### 4.1 场景一：修图版本自动记录

用户创建一个项目文件夹：

```text
客户A写真修图/
  原片/
  精修中/
  导出/
```

用户正常使用 PS、醒图、美图秀秀、像素蛋糕等工具修图。

当图片被新增、覆盖、导出、重命名时，系统自动生成快照。

### 4.2 场景二：查看每个版本差异

用户点击某张图，可以看到版本时间线：

```text
IMG_2031 版本历史

v1  14:02  原始导入
v2  14:26  Photoshop 导出
v3  14:41  醒图二次调色
v4  15:10  客户反馈修改
v5  15:34  最终交付版
```

用户可以选择任意两个版本进行对比。

### 4.3 场景三：客户要求回到上一版

客户说：

> 还是上一版自然一点。

用户打开版本历史，找到 v3，点击“恢复为当前版本”。

系统不直接覆盖历史，而是生成新版本：

```text
v6：从 v3 恢复
```

这样历史不会丢。

### 4.4 场景四：自动生成修图说明

AI 自动生成：

```text
相比 v3，v4 主要进行了以下修改：

1. 人物面部整体提亮，肤色更白。
2. 皮肤纹理减少，视觉上更接近磨皮效果。
3. 背景亮度降低，人物主体更突出。
4. 整体色温略微偏冷，画面更干净。
5. 图片经过轻微裁剪，右侧边缘内容减少。
```

也可以生成客户友好版：

```text
已优化人物肤色和背景氛围，整体更加干净自然。
```

## 5. MVP 核心功能

第一版建议只做 5 个核心模块。

---

### 5.1 模块一：项目文件夹监听

用户选择一个或多个文件夹，系统开始监听。

监听事件包括：

- 新增图片
- 图片被覆盖
- 图片被重命名
- 图片被导出
- 图片尺寸变化
- 图片格式变化
- 图片内容变化

系统检测到变化后，自动生成一个快照。

---

### 5.2 模块二：自动版本分组

系统自动判断哪些图片属于同一张图的不同版本。

例如：

```text
IMG_2031.jpg
IMG_2031_修图.jpg
IMG_2031_final.jpg
IMG_2031_final2.jpg
IMG_2031_醒图导出.jpg
```

应该被归为同一个版本组：

```text
IMG_2031
  v1 原图
  v2 初修
  v3 醒图调色
  v4 客户修改
  v5 最终版
```

可用于判断版本归属的信号：

- 文件名相似度
- 图片感知哈希
- 拍摄时间
- EXIF 信息
- 图像主体相似度
- 尺寸比例
- 创建时间
- 文件夹路径

---

### 5.3 模块三：版本时间线

每张图都有一个版本时间线。

每个版本支持：

- 查看
- 对比
- 回退
- 添加备注
- 标记为最终版
- 标记为客户确认版
- 导出
- 删除

示例：

```text
v1 原图
v2 初调色
v3 磨皮
v4 客户二修
v5 最终版
```

---

### 5.4 模块四：图片 Diff

Diff 是产品的核心差异化之一。

第一版至少做三种 Diff。

#### 5.4.1 滑杆对比

最直观的对比方式。

适合快速判断：

- 脸有没有变白
- 背景有没有变暗
- 构图有没有裁掉
- 滤镜有没有变重
- 商品主体有没有被改动

#### 5.4.2 热力图 Diff

系统标出变化区域：

```text
红色：变化明显
黄色：轻微变化
透明：基本无变化
```

示例输出：

```text
主要变化区域：
- 面部
- 背景右侧
- 头发边缘
- 图片下方文字
```

#### 5.4.3 结构化变化指标

输出一些相对客观的信息：

```text
亮度：+12%
饱和度：-6%
对比度：+8%
清晰度：+4%
肤色区域亮度：+15%
背景亮度：-10%
图片尺寸：4032×3024 → 3000×2250
文件大小：4.8MB → 1.3MB
```

这些指标对专业用户、电商运营、修图团队更有价值。

---

### 5.5 模块五：AI 变化总结

AI 不应该声称知道用户用了哪个软件或哪个滤镜，而应该总结视觉结果。

推荐表达：

```text
面部皮肤纹理减少，视觉上更接近磨皮效果。
```

不推荐表达：

```text
用户使用了醒图磨皮工具。
```

AI 总结可以提供三种口吻。

#### 给自己看

```text
面部提亮，肤色变白，背景压暗，磨皮增强。
```

#### 给客户看

```text
已优化肤色和背景，人物更突出，整体效果更干净自然。
```

#### 给团队看

```text
本版本主要完成肤色调整、背景弱化和面部细节优化，适合作为二修交付版。
```

## 8. Diff 技术方案

第一版可以完全基于两个图片文件做。

### 8.1 基础流程

```text
输入 v1 和 v2
↓
读取文件信息
↓
统一尺寸、方向、色彩空间
↓
判断是否需要对齐
↓
计算像素差异
↓
计算感知差异
↓
识别人脸 / 主体 / 背景区域
↓
生成热力图
↓
生成结构化指标
↓
交给 AI 生成自然语言总结
```

### 8.2 确定性结果

这些结果比较可靠：

- 尺寸变化
- 格式变化
- 亮度变化
- 饱和度变化
- 对比度变化
- 清晰度变化
- 主要变化区域
- 裁剪 / 缩放 / 旋转
- 文件大小变化
- EXIF 是否丢失

### 8.3 AI 推断结果

这些结果需要使用谨慎措辞：

- 视觉上更像磨皮
- 肤色更白
- 背景更干净
- 主体更突出
- 风格更偏商业精修
- 氛围更柔和

### 8.4 不应承诺的能力

仅凭两张图，不能可靠判断：

- 用户具体用了哪个软件
- 用户用了哪个滤镜名称
- 用户在 PS 或 LR 里调了哪个参数
- 完整修图步骤
- 所有操作的先后顺序

## 9. 置信度系统

每次 AI 总结旁边建议显示：

```text
分析可信度：高 / 中 / 低
```

### 高可信示例

```text
分析可信度：高

原因：两张图片构图一致，主体位置基本相同，适合进行视觉 Diff。
```

### 中可信示例

```text
分析可信度：中

原因：新版图片经过裁剪和重新压缩，细节变化可能部分来自导出压缩。
```

### 低可信示例

```text
分析可信度：低

原因：两张图片构图变化较大，系统只能总结整体视觉差异，无法准确定位所有修改。
```

这个设计可以提升用户信任，也能避免 AI 过度解释。

## 11. 技术架构初版

### 11.1 产品形态

建议第一版做成：

> 桌面端本地优先应用。

原因：

- 用户图片大多在本地电脑
- 方便监听文件夹
- 方便读取大图
- 方便保存快照
- 离线可用
- 隐私感更好

### 11.2 技术选型建议

| 模块 | 推荐方案 |
|---|---|
| 桌面框架 | Tauri / Electron |
| 本地数据库 | SQLite |
| 图片处理 | OpenCV / Sharp / ImageMagick |
| 缩略图缓存 | 本地缓存 |
| 快照存储 | 内容哈希 + 本地对象存储 |
| AI 总结 | 云端多模态模型，后续支持本地模型 |
| 同步 | 第二阶段再做云同步 |

### 11.3 本地目录结构

```text
PhotoHistoryApp/
  projects/
    project_001/
      assets/
      snapshots/
        asset_001/
          v001.jpg
          v002.jpg
          v003.jpg
      diffs/
        asset_001/
          v001_v002_diff.png
          v002_v003_diff.png
      metadata.db
```

## 12. 存储策略

### 12.1 初版策略

- 每次快照保存完整图片
- 生成缩略图
- 生成预览图
- 用 hash 去重
- 用户可设置最大缓存空间

### 12.2 后续优化

- RAW / PSD 大文件只做索引
- JPG / PNG / WEBP 保存快照
- 大图可以压缩预览
- 原始文件可外部归档
- 企业版支持云对象存储
- 未来引入类似 Git LFS 的对象存储机制

第一版不要过度优化“增量存储”，先保证稳定、可理解、可恢复。

## 13. AI 总结设计

AI 总结不要只把两张图扔给模型，最好先生成结构化 Diff，再让 AI 结合图片和数据总结。

### 13.1 AI 输入

- 旧版图片
- 新版图片
- 热力图
- 亮度变化
- 饱和度变化
- 对比度变化
- 主要变化区域
- 是否裁剪
- 是否压缩
- 用户备注

### 13.2 AI 输出

```json
{
  "short_summary": "面部提亮，背景压暗，肤色更白。",
  "detailed_summary": [
    "人物面部亮度提升，肤色更白。",
    "背景区域亮度降低，主体更突出。",
    "面部皮肤纹理减少，视觉上更平滑。"

  "confidence": "medium",
  "warnings": [
    "新版图片存在重新压缩，部分细节变化可能来自导出。"
  ]
}
```

## 14. 产品差异化

你的产品不是修图软件，也不是网盘，也不是普通相册。

| 普通相册 | 修图软件历史 | 本产品 |
|---|---|---|
| 只保存图片 | 只管软件内部操作 | 跨软件保存版本 |
| 难比较两版 | 会话内历史为主 | 长期版本时间线 |
| 没有 Diff | 有前后对比但通常不总结 | 可视化 Diff + AI 总结 |
| 不懂修图变化 | 偏操作层 | 偏结果层和交付层 |
| 适合个人浏览 | 适合单次编辑 | 适合多轮修改和协作 |

一句话差异化：

> 不是替代 PS、醒图、美图、像素蛋糕，而是成为它们外面的版本记录层。

## 17. 早期验证方式

### 17.1 Demo 1：两图 Diff 网页

用户上传两张图，系统输出：

- 热力图

- 可信度

目标：验证 Diff 和 AI 总结有没有价值。

### 17.2 Demo 2：本地文件夹监听

如果这个场景成立，产品价值就很强。

## 18. MVP 成功指标

MVP 不应该只看下载量，而应该看行为指标：

- 用户平均每个项目生成多少版本
- 用户是否会回看旧版本
- 用户是否会使用 Diff
- 用户是否会复制 AI 总结
- 用户是否会标记最终版
- 用户是否会恢复旧版本
- 用户是否愿意把它用于真实客户项目

最关键的指标是：

> 用户是否在真实修图工作流里持续使用，而不是只试一次。

## 20. Agent 最终形态

Agent 不建议第一天就做，但这个产品天然适合加 Agent。

原因是系统会积累大量上下文：

- 原图
- 每个版本
- 每次 Diff
- AI 总结
- 用户备注
- 客户反馈
- 最终交付结果

未来 Agent 可以回答或执行：

```text
帮我找肤色最自然的一版。
这张图客户到底改了几轮？
帮我总结今天完成了哪些修图。
检查这一组图风格是否一致。
根据客户反馈生成修图待办。
帮我判断哪版适合发小红书。
把这组图的交付说明写出来。
```

Agent 方向会成为长期壁垒。

## 21. 最终建议

第一版建议收敛成：

> 本地优先的“修图版本时间线”。

核心能力：

- 用户选择文件夹后，系统自动记录每一次图片变化
- 生成版本历史
- 支持滑杆对比
- 支持热力图 Diff
- 用 AI 总结每次修改
- 支持快速找回旧版本
- 支持标记最终交付版

这是最轻、最稳、也最容易验证市场的切入点。

---

## 22. 最终一句话方案

> 第一版做一个本地优先的“修图版本时间线”：用户选择文件夹后，系统自动记录每一次图片变化，生成版本历史、滑杆对比、热力图 Diff 和 AI 变化总结，让用户可以快速看懂每版改了什么，并随时回到旧版本。
